## 4.1 `typescript.md` 用原文（TypeScript 規約）

### 型安全の基本
- **`any` 型禁止** → `unknown` + 型ガードを使用
- **`as` キャスト最小化** → 型ガード関数で安全に絞り込む
- **暗黙の `any` 禁止** → `tsconfig.json` で `strict: true`

```typescript
// ❌ 禁止
const data: any = fetchData();
// ✅ 推奨
const data: unknown = fetchData();
if (isOrder(data)) {
  console.log(data.orderId); // 型安全
}
function isOrder(value: unknown): value is Order {
  return typeof value === 'object' && value !== null && 'orderId' in value;
}
```

### Interface vs Type Alias

| 使い分け | 選択 |
|----------|------|
| オブジェクト形状（Props, API Response） | `interface` |
| Union型、Intersection型、ユーティリティ型 | `type` |
| 拡張が必要（`extends`）| `interface` |

```typescript
// Props → interface
interface OrderListProps {
  readonly orders: Order[];
  readonly onSelect: (id: string) => void;
}
// Union → type
type OrderStatus = 'pending' | 'confirmed' | 'shipped' | 'cancelled';
```

### 命名規則

| 対象 | 規則 | 例 |
|------|------|------|
| 型/Interface | PascalCase | `OrderResponse`, `UserProfile` |
| 関数 | camelCase + 動詞 | `handleSubmit`, `fetchOrders` |
| 定数 | UPPER_SNAKE_CASE | `MAX_RETRY_COUNT`, `API_BASE_URL` |
| boolean変数 | is/has/can 接頭辞 | `isLoading`, `hasError`, `canEdit` |
| イベント | handle 接頭辞 | `handleClick`, `handleChange` |

### JSDoc

JSDoc は必ず記述すること。
- **実装で自明なことは書かない**: 型から明白な振る舞いや型情報は繰り返さない
- **意図を説明する**: 目的・典型例・副作用を記述する
- **共通・再利用コンポーネントには画面IDを記載しない**（機能固有コンポーネントのみ記載可。※このプロジェクトの画面ID命名規則が確定次第、具体例を補記する）

| `@example` | 使用例 |
| `@remarks` | 補足情報・注意点 |
| `@deprecated` | 非推奨の理由と代替 |

## 4.2 `react-component.md` 用原文（React コンポーネント規約）

### 基本原則
2. **可読性優先**: 凝ったコードより読みやすいコード
3. **型安全**: `any` 型禁止 → `unknown` + 型ガード
4. **React ベストプラクティス**: 公式ドキュメントに準拠

### コンポーネント設計

#### 単一責任
- 1コンポーネントは1つの関心事のみ
- 300行以上のコンポーネントは分割を検討
- UI表示とビジネスロジックを分離（カスタムフック活用）

#### Props 設計
```tsx
// ✅ 明示的な Props 型定義（interface を使用）
interface OrderListProps {
  readonly orders: Order[];
  readonly isLoading: boolean;
  readonly onSelect: (orderId: string) => void;
}
export const OrderList: React.FC<OrderListProps> = ({ orders, isLoading, onSelect }) => {
  // ...
};
```
- **Props 定義は `interface` を使用**（拡張・継承・一貫性のため）
- Union / Intersection など複雑な型合成には `type` を使用
- Props は `readonly` を付与
- コールバックは `on` 接頭辞: `onSelect`, `onChange`, `onSubmit`
- boolean Props は `is`/`has`/`can` 接頭辞: `isLoading`, `hasError`
- デフォルト値は分割代入で指定

#### コンポジション
- 継承より合成（Composition over Inheritance）
- `children` Props を活用
- Compound Component パターンで複雑なUIを構成

### パフォーマンス最適化
```tsx
// React.memo — Props が変わらない場合の再レンダリング防止
export const OrderRow = React.memo<OrderRowProps>(({ order, onSelect }) => {
  // ...
});
// useCallback — コールバック関数の参照安定化
const handleSelect = useCallback((orderId: string) => {
  onSelect(orderId);
}, [onSelect]);
// useMemo — 重い計算結果のキャッシュ
const sortedOrders = useMemo(
  () => orders.sort((a, b) => b.createdAt - a.createdAt),
  [orders]
);
```
- `React.memo`: リスト項目、頻繁に再レンダリングされるコンポーネント
- `useCallback`: 子コンポーネントに渡すコールバック
- `useMemo`: ソート、フィルタ、集計などの重い計算

### 状態管理
- **ローカル状態**: `useState` / `useReducer`（コンポーネント内完結）
- **サーバー状態**: TanStack Query 等（API通信のキャッシュ・同期）
- **フォーム状態**: React Hook Form 等（バリデーション連携）

### ファイル命名

| 種別 | 命名 | 例 |
|------|------|------|
| ページコンポーネント | `*Page.tsx` | `OrderListPage.tsx` |
| レイアウト | `*Layout.tsx` | `MainLayout.tsx` |
| フォーム | `*Form.tsx` | `OrderForm.tsx` |
| モーダル | `*Modal.tsx` | `ConfirmModal.tsx` |
| カスタムフック | `use*.ts` | `useOrderList.ts` |
| サービス | `*Service.ts` | `orderService.ts` |
| 型定義 | `*.types.ts` | `order.types.ts` |
| テスト | `*.test.tsx` | `OrderList.test.tsx` |

### テスト配置
- テストファイル（`*.test.tsx`, `*.test.ts`）は機能ディレクトリ配下の `__tests__/` に配置する
- `__test__/`（単数）のディレクトリ名は使用しない
- 実装ファイルと同階層にテストファイルを配置しない

> ※このプロジェクトでは `features/[機能名]/tests/` 配下に配置する方針（6.2 react-generator の指示）と整合させること。`__tests__/` か `tests/` かは案件確定時に統一する。

### アクセシビリティ
- セマンティックHTML要素を使用（`<button>`, `<nav>`, `<main>` 等）
- ARIA属性は必要最小限
- フォーカス管理を考慮（モーダル、ドロップダウン）
- キーボード操作をサポート

## 4.3 `react-validation.md` 用原文（フォームバリデーションルール）



### バリデーション実装方針
- **推奨**: Zod + React Hook Form (`zodResolver`)
- バリデーションスキーマは `*.types.ts` または `*.schema.ts` に定義
- エラーメッセージは画面仕様書の文言に従う（未指定の場合は下表のデフォルト文言を使用）
- バリデーションエラー時は API を呼び出さない（クライアント側でブロック）

### 画面仕様書の制約 → バリデーションスキーマ マッピング

| 画面仕様書の制約 | Zod スキーマ | エラーメッセージ例 |
|:---|:---|:---|
| 必須項目 | `z.string().min(1, ...)` | `"○○は必須です"` |
| 最大文字数 N | `z.string().max(N, ...)` | `"○○はN文字以内で入力してください"` |
| 最小文字数 N | `z.string().min(N, ...)` | `"○○はN文字以上で入力してください"` |
| 数値のみ | `z.string().regex(/^[0-9]+$/, ...)` | `"○○は数値で入力してください"` |
| 半角英数字 | `z.string().regex(/^[a-zA-Z0-9]+$/, ...)` | `"○○は半角英数字で入力してください"` |
| 全角文字のみ | `z.string().regex(/^[^\x01-\x7E]+$/, ...)` | `"○○は全角文字で入力してください"` |
| パターン（正規表現） | `z.string().regex(pattern, ...)` | `"○○の形式が正しくありません"` |
| 数値範囲 min〜max | `z.number().min(min).max(max)` | `"○○はmin〜maxの範囲で入力してください"` |
| 日付形式 | `z.string().regex(/^\d{4}-\d{2}-\d{2}$/, ...)` | `"○○は日付形式で入力してください"` |
| 配列最小要素数 N | `z.array(...).min(N, ...)` | `"○○はN件以上選択してください"` |

## 5.1 `react-self-check` Skill 用原文（Reactレビュー観点）

### レビュー観点（10項目）

**A. コード品質**
1. 不要なファイル・コードがないこと
6. 変数名、関数名、コンポーネント名が命名規則に則っていること
8. 可読性を考慮していること

**B. アーキテクチャ・責務分離**
2. 適切なファイルに責務を分離させていること
3. 共通部品を適切に使用していること
9. 保守性を考慮していること

**C. 型・スタイリング**
4. スタイリングを適切に設定していること
5. 型定義を適切に設定していること

**D. パフォーマンス・セキュリティ**
7. パフォーマンスを考慮していること
10. XSS脆弱性がないこと

### 指摘形式

```
指摘ラベル: {ラベル}
修正箇所: ファイル・行数を記載
指摘内容: 具体的な指摘内容を記載
```

| ラベル | 意味       | 用途 |
|--------|------------|------|
| must   | 必須修正   | セキュリティ、バグ、仕様違反、型エラーなど |
| should | 推奨修正   | 修正した方が良いが必須ではない点 |
| nit    | 些細な指摘 | スペース、軽微な命名、コメント表現など |
| ask    | 要確認     | 業務仕様・設計方針など判断が必要な点 |

### 詳細補足

#### 1. 不要なファイル・コードがないこと
- `.gitkeep` など不要なファイルが残っていないこと
- 使用していない import、変数、関数、コンポーネントが残っていないこと
- デバッグ用のコード（`console.log` 等）が残留していないこと
- `ErrorBoundary` は使用していないこと
- コメントアウトされた古いコードが残っていないこと

#### 2. 適切なファイルに責務を分離させていること

フォルダ構成は以下の構成を想定している。各ファイルの役割に合わせてコードを集約させること:

```
features/
├── [機能名]/
│   ├── components/  # コンポーネントの定義・UI表示用の処理の定義。UI表示以外の用途の関数・定数以外は定義しない
│   ├── hooks/       # ビジネスロジック、状態管理、API呼び出しなどの副作用を伴う主要な関数（コンポーネント単位で状態管理はしない）
│   ├── services/    # APIリクエストを行う関数の定義
│   ├── types/
│   │   ├── *.types.ts   # 機能内で使用している interface、type の定義（基本的にすべての型定義をこのファイルに集約）
│   │   ├── *.schema.ts  # バリデーション用の設定ファイル
│   │   └── index.ts     # 上記2ファイルの定義を export するだけ
│   └── index.tsx
```

確認観点:
- ビジネスロジックが components/ に混在していないこと
- API 呼び出しが hooks/ や components/ に直接記述されていないこと（services/ に集約）
- 型定義が各ファイルに散在せず types/ に集約されていること
- 複数コンポーネントで共有される状態が hooks/ で管理されていること

#### 4. スタイリングを適切に設定していること
- `style` 属性を使用せず、Tailwind CSS（`className` 属性）でスタイリングしていること
- スタイリングのために `useEffect` を使用していないこと
- レイアウトに影響しないスタイリング用クラスが設定されていないこと
- 余分なHTMLエレメントがなく、最低限の構成になっていること
- インラインスタイルが残っていないこと

#### 5. 型定義を適切に設定していること
- 型エラーがないこと
- 値がない状態の型は、APIレスポンスは `null`、それ以外は `undefined` を使用すること
- `interface` の `readonly` を使用しないこと
- オブジェクトの形状定義は `interface`、型の合成やプリミティブ型エイリアスは `type` を使用すること
- `as` による型キャストを使用しないこと
- 関数の引数と返却値に `any` を避け、型安全な型を明示的に指定すること
- `unknown` + 型ガードを使用して型安全性を確保すること

#### 6. 変数名、関数名、コンポーネント名が命名規則に則っていること
- 変数名・関数名は必ず英語で命名すること
- コンポーネント名に `Component` を付けないこと（冗長なため禁止）
- 略語禁止（例: `orderNum` → `orderNumber`）
- Boolean 変数・関数は `is` / `has` / `can` 等の意味が自然な名前にすること
- イベントハンドラ関数は `handle` プレフィックスを使用すること（例: `handleSubmit`）
- カスタムフックは `use` プレフィックスを使用すること

#### 7. パフォーマンスを考慮していること
- DRY になっていること
- API呼び出し以外では極力 `useEffect` を使用していないこと
- 複数回呼び出される変数や関数は `useMemo` / `useCallback` を適切に使用し、計算コストが低い処理へのむやみな適用は避けること
- 状態管理の必要がない値は `useState` を使わないこと
- 不要な再レンダリングが発生しないようになっていること
- 大きなリストのレンダリングに仮想化（Virtualizer 等）が必要かどうかを検討していること

#### 8. 可読性を考慮していること
- 過剰なコメントがないこと（変数名・関数名・型だけで意味が分かるコードにはコメントをつけない）
- コメントがなくても処理内容がわかるような記載になっていること
- 「何をしているか」ではなく「なぜそうしているか」のコメントが記載されていること
- 複雑な条件式が意味のある変数や関数に分解されていること
- マジックナンバー・マジック文字列が定数化されていること

#### 9. 保守性を考慮していること
- バリデーションを行うフォームは `zod` と `react-hook-form` を使用すること
- 定数値はマスタが存在する場合、ハードコーディングせずマスタから取得すること
- 複数箇所で使用されるロジックは共通化されていること

#### 10. XSS脆弱性がないこと
- `dangerouslySetInnerHTML` を使用していないこと
- ユーザー入力・外部データを直接HTMLに挿入していないこと
- 外部リンクに `target="_blank"` を使用する場合は `rel="noopener noreferrer"` を設定していること
- URLを動的に構築している場合、`encodeURIComponent` 等でエスケープしていること
